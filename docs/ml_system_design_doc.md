### 1. Цели и предпосылки 
#### 1.1. Зачем идем в разработку продукта?  

- **Бизнес-цель**: Создание специализированного фреймворка для дообучения Vision-Language Model (VLM) с использованием LoRA (Low-Rank Adaptation) для описания русских персонажей на изображениях
- **Почему станет лучше**: Существующие VLM плохо понимают русские культурные персонажи и контексты. Специализированное дообучение позволит улучшить качество описания русских персонажей на изображениях
- **Критерии успеха итерации**: Создание рабочего MVP фреймворка с демонстрацией улучшения качества описания русских персонажей на тестовом датасете изображений

#### 1.2. Бизнес-требования и ограничения  

- **Бизнес-требования**: 
  - Создание воспроизводимого фреймворка для LoRA дообучения VLM
  - Поддержка различных архитектур Vision-Language моделей
  - Возможность быстрого прототипирования и экспериментов с изображениями
  - Документированный процесс дообучения для описания русских персонажей
- **Бизнес-ограничения**: 
  - Ограниченные вычислительные ресурсы (GPU)
  - Необходимость сохранения базовых способностей модели
  - Требования к воспроизводимости экспериментов
- **Ожидания от итерации**: Создание MVP фреймворка с примером дообучения на изображениях русских персонажей
- **Бизнес-процесс пилота**: Тестирование фреймворка на датасете изображений с русскими персонажами с измерением CLIP Score
- **Критерии успешного пилота**: Улучшение CLIP Score с ruCLIP для описания русских персонажей по сравнению с базовой VLM (конкретные метрики будут определены после тестирования)

#### 1.3. Что входит в скоуп проекта/итерации, что не входит   

- **Входит в скоуп**:
  - Создание базового фреймворка для LoRA дообучения VLM
  - Подготовка датасета изображений с русскими персонажами
  - Реализация пайплайна дообучения для описания изображений
  - Базовые метрики оценки качества (CLIP Score с ruCLIP)
  - Документация по использованию
- **Не входит в скоуп**:
  - Production-ready система развертывания
  - Автоматическое масштабирование
  - Продвинутые техники оптимизации
  - Интеграция с внешними системами
- **Результат с точки зрения качества кода**: Чистый, документированный код с примерами использования и воспроизводимыми экспериментами
- **Технический долг**: Отсутствие автоматического мониторинга, ограниченная поддержка различных форматов данных, базовый интерфейс

#### 1.4. Предпосылки решения  

- **Блоки данных**: Датасет изображений с русскими персонажами и их текстовые описания
- **Горизонт прогноза**: Не применимо (задача генерации текста по изображению)
- **Гранулярность модели**: Описание изображений на уровне персонажей и их характеристик
- **Частота пересчета**: По требованию (offline обучение)
- **Обоснование**: LoRA позволяет эффективно дообучать большие VLM с минимальными вычислительными затратами, сохраняя базовые способности модели

### 2. Методология     

#### 2.1. Постановка задачи  

- **Техническая задача**: Создание системы дообучения Vision-Language Model (VLM) с использованием LoRA для описания русских персонажей с изображений
- **Тип задачи**: Supervised Fine-Tuning (SFT) для задачи генерации текстовых описаний изображений с русскими культурными персонажами
- **Цель**: Адаптировать предобученную VLM для лучшего понимания и описания русских культурных персонажей на изображениях

#### 2.2. Блок-схема решения  

```
[Изображения с русскими] → [Подготовка датасета] → [Предобработка] → [LoRA дообучение] → [Валидация] → [Тестирование] → [Деплой модели]
[персонажами]            ↓                    ↓                ↓                ↓              ↓              ↓
                        [Разметка описаний]  [Vision Encoder] [Fine-tuning]   [CLIP Score]  [Image-to-Text] [Модель готова]
                        [Train/Val/Test]    [Text Decoder]   [LoRA layers]   [ruCLIP]     [Generation]    [к использованию]
```


#### 2.3. Этапы решения задачи

**Этап 1. Подготовка данных**

Описание данных / сущностей
- Источник: локальная директория `data/images/` (папки по персонажам: `alyosha`, `cheburashka`, `gena`, `kolobok`) и примеры в `assets/` (используются для sanity-check и репликации результатов). Аннотации хранятся в `data/annotation.json`, а базовые промпты — в `data/json/base_prompts.json`.
- Формат аннотаций: JSON-массив объектов с полями: путь к изображению, (при необходимости) путь к конвертированному изображению, имя персонажа/папки, использованный промпт, сгенерированный ответ (caption) и дополнительные поля (meta, quality tags).

Выявленные проблемы (результаты EDA)
- Объём: текущий репозиторий содержит демонстрационный набор (десятки изображений на персонажа). Для устойчивого дообучения VLM этого недостаточно — ожидаемый целевой объём: ~200–500 изображений на ключевую сущность.
- Качество разметки: подписи генерируются автоматически (скрипт `caption_data.py` использует GigaChat), присутствует шум и вариативность качества, возможны некорректные или слишком короткие ответы.
- Форматы/качество изображений: присутствуют разные форматы (webp, png, jpg); часть изображений требует конвертации/очистки и проверки разрешения.

Риски, выявленные на этапе EDA
- Переобучение на малом объёме данных → решение: увеличить набор данных, применять augmentation, использовать LoRA (адаптация небольшого числа параметров) и регуляризацию.
- Шумные/плохие подписи → решение: автоматические фильтры качества (длина, стоп-слова), семплинг для ручной проверки, пометка низкокачественных записей для доразметки.
- Коррупция/несоответствие форматов → добавить автоматическую проверку целостности изображений и конвертацию в единую схему предобработки.

Процесс генерации данных
- Скрипт: `caption_data.py` проходит по `data/images/`, при необходимости конвертирует webp→png, отправляет изображения в генератор (GigaChat в текущем пайплайне), сохраняет промпт и ответ в `data/annotation.json` инкрементально.
- Частота: параметризуемый процесс — однократно при наполнении датасета или периодически (например, при добавлении новых пакетов изображений). Рекомендуется запускать с валидацией качества после каждой крупной итерации.

Если данных недостаточно — пути решения и оценка объёма
- Источники: краулинг/скрейпинг релевантных изображений, краудсорсинг аннотаций, использование публичных датасетов с фильтрацией релевантности, синтетическая генерация и аугментации.
- Оценка: для минимально надёжного SFT/LoRA рекомендуем целевой объём ~200–500 изображений на сущность; для 4–10 сущностей — 800–5000 изображений в сумме.

Конфиденциальность
- Текущие данные — публичные изображения персонажей, персональных данных нет. При расширении датасета необходимо фильтровать изображения с реальными лицами, документами или приватной информацией; при необходимости применять маскирование/анонимизацию.

Необходимый результат этапа
- Отфильтрованный и частично верифицированный `data/annotation.json` с метаданными, набор скриптов для инкрементальной генерации/очистки, EDA-отчёт (ноутбук) с распределением по классам и примерами ошибок, gold-set (ручная верификация 100–300 примеров).

Полезные рекомендации
- Хранить версии промптов и модели, seed генерации и метрики качества (например, длина ответа, индикаторы токсичности) для аудита и репликации экспериментов.

**Этап 2. Подготовка прогнозных моделей**

Описание ML-метрик и функций потерь
- Основная метрика: CLIP Score (рекомендуется использовать ruCLIP или адаптированный CLIP для русского языка) — измеряет семантическую соответствие между изображением и сгенерированным текстом.
- Вспомогательные метрики: CIDEr / SPICE / BLEU / ROUGE — для дополнительного сравнения, но не как единственный критерий.
- Функция потерь при обучении: token-level Cross-Entropy (teacher forcing). В продвинутых конфигурациях — комбинированный лосс: CE + contrastive (CLIP-guided) компонент для улучшения соответствия text↔image.

Схема ML-валидации
- Разбиение: рекомендуемый базовый split — stratified 80/10/10 (train/val/test) по папкам/персонажам. При малых объёмах — использовать k-fold (например, 5-fold) или group-based CV, чтобы оценка была более стабильной.
- Валидация: отслеживать CLIP Score на валидации и loss (CE); периодически проводить human-in-the-loop проверку по gold-set для оценки фактического качества.
- Контроль деградации: включить контрольные тесты на общем наборе сущностей (Spiderman/Superman из `assets/`) чтобы убедиться, что дообучение не ломает общие знания модели.

Структура бейзлайна (baseline)
- Модель: использовать предобученную VLM (в ноутбуке — `Qwen/Qwen3-VL-2B-Instruct` как пример baseline). Дообучать только LoRA-адаптеры (минимальный набор весов).
- Предобработка: конвертация изображений в единый формат, изменение размера/нормализация, токенизация текстов с ограничением max_length.
- Тренировка: AdamW для LoRA-параметров, начальный lr в диапазоне 1e-5–5e-4 (тестировать), batch size и gradient accumulation под доступные ресурсы, mixed-precision при возможности.
- Checkpointing: сохранять LoRA-слои и связанный сессийный мета-файл (промпты, версия модели, seed, используемые метрики).

Предобработка и pipeline бейзлайна
- Preproc: фильтрация повреждённых/слишком маленьких изображений, базовые аугментации (flip, color jitter), нормализация; очистка и фильтрация шумных caption-ов.
- LoRA-параметры: тестировать ранги r=8..64, применять LoRA к attention/MLP слоям в decoder/encoder в зависимости от архитектуры.

Стратегии развития
- Модели: тестировать как более лёгкие (для latency) так и более крупные модели (для качества); рассмотреть multi-task обучение (caption + classification) и distillation.
- HPO: автоматизированный поиск гиперпараметров (Optuna, ASHA), ранний стоп по CLIP Score.
- Data-centric: улучшать качество caption-ов, расширять датасет, добавлять метки качества и human-feedback loop.

Анализ и интерпретация
- Сравнивать распределения CLIP Score до/после дообучения по классам; формировать списки лучших и худших примеров для ручной проверки.
- Визуализировать attention/heatmaps (если доступны) и анализировать типичные ошибки (путаница персонажей, неправильные атрибуты).

Риски и смягчение
- Переобучение: augmentation, регуляризация, ранний стоп.
- Деградация общих навыков модели: ограничение обучения LoRA, интеграция контрольных тестов на общем датасете.
- Ограниченные ресурсы: LoRA, уменьшение batch size, gradient accumulation, использование fp16/bf16.

Необходимый результат этапа
- Доступный pipeline обучения LoRA с reproducible скриптами, checkpoint-ы LoRA, метрики (CLIP Score/loss) и итоговый отчёт с визуализациями и примерами генераций.

Полезные рекомендации
- Зафиксировать baseline (версию VLM, `assets/` и `data/json/base_prompts.json`) и набор тестовых промптов/seed для воспроизводимости и корректного сравнения экспериментов.

  - Зафиксировать версию baseline-модели и набор тестовых изображений (`assets/`), чтобы сравнения CLIP Score и human-eval были воспроизводимыми.
  - При валидации после дообучения обязательно запускать inference по базовому набору сущностей (gold set), включая как локальные русские персонажи, так и общие знакомые объекты (Spiderman/Superman) — проверка на деградацию знаний.
  - Сохранить примеры промптов и seed для случайной выборки валидации, чтобы результаты сравнимы между экспериментами.

**Этап 3 - Валидация и тестирование**

- **Техника**: Кросс-валидация на размеченном датасете изображений, A/B тестирование с базовой VLM. Для малого датасета использовать k-fold или leave-one-group-out по папкам персонажей.
- **Метрики**: CLIP Score (основная), CIDEr/SPICE (вспомогательно), human-eval для финальной выборки.
- **Результат**: Набор метрик по train/val/test, отчёт с примерами генераций и сравнением с базовой моделью.

### Этапы, специфичные для этой задачи (рекомендованные)

1) Автоматическая генерация и очистка captions
  - Скрипт `caption_data.py` уже реализует генерацию через GigaChat и конвертацию webp. На этапе EDA рекомендовано расширить постобработку: фильтрация коротких/пустых ответов, выделение и пометка сомнительных записей для ручной проверки.

2) Data augmentation и синтетика
  - Генерация вариаций изображений (flip, crop, color jitter); при необходимости — генерация синтетики через image-to-image модели, чтобы увеличить дисперсию фона/ракурса у персонажей.

3) Gold set и ручная верификация
  - Отобрать 100–300 эталонных изображений с качественными captions для оценки модели и fine-grained ручной проверки (human-in-the-loop). Это поможет калибровке CLIP Score под задачу.

4) CI для аннотаций и обучения
  - Добавить простые тесты/валидации: проверка целостности `annotation.json`, отсутствие дублирующихся записей, минимальная длина captions, корректность полей. Интегрировать эти проверки в pre-commit или CI workflow.

5) Визуализации и отчёт EDA
  - Нотбук/скрипт с графиками: распределение по классам, histogram длины captions, количество конвертированных webp файлов, примеры лучших/худших caption-генераций. Результат — `finetune_testing/eda_report.md` или `notebook` добавленный в репозиторий.

Эти специфичные этапы напрямую следуют из EDA и текущего пайплайна в репозитории и их реализация минимально затратна, но существенно повысит надёжность финального решения.

### 3. Подготовка пилота  

#### 3.1. Способ оценки пилота  

- **Дизайн пилота**: Сравнительное тестирование базовой и дообученной VLM на тестовом датасете изображений с русскими персонажами
- **Методология**: A/B тестирование с метрикой CLIP Score с ruCLIP

#### 3.2. Что считаем успешным пилотом  

- **Метрики успешности**:
  - Улучшение CLIP Score с ruCLIP для описания русских персонажей (целевые значения будут определены после тестирования)
  - Положительный CLIP Score с ruCLIP для соответствия между изображениями и текстовыми описаниями
  - Улучшение относительно базовой VLM (масштаб будет определен экспериментально)
  - Сохранение качества на общих задачах описания изображений (не деградация)

#### 3.3. Подготовка пилота  

- **Вычислительная сложность**: Оценка на основе размера модели и датасета
- **Ограничения**: GPU память, время обучения, размер LoRA адаптеров
- **Планирование**: Поэтапное увеличение сложности экспериментов

### 4. Внедрение    

#### 4.1. Архитектура решения   

- **Компоненты**:
  - Data preprocessing pipeline
  - LoRA training framework
  - Model evaluation tools
  - Inference API
- **API методы**: train(), evaluate(), predict(), load_model()

#### 4.2. Описание инфраструктуры и масштабируемости 

- **Инфраструктура**: Локальная разработка с возможностью масштабирования на облачные GPU
- **Плюсы**: Гибкость, контроль над данными
- **Минусы**: Ограниченные ресурсы, необходимость ручного управления
- **Обоснование**: MVP требует простоты и контроля над процессом

#### 4.3. Требования к работе системы  

- **SLA**: Offline обучение, время отклика inference < 1 сек
- **Пропускная способность**: Обработка текстов до 1000 токенов в секунду
- **Задержка**: < 100ms для inference

#### 4.4. Безопасность системы  

- **Уязвимости**: Потенциальные атаки на модель через adversarial examples
- **Меры**: Валидация входных данных, ограничение размера запросов

#### 4.5. Безопасность данных   

- **GDPR**: Использование только публичных датасетов, отсутствие персональных данных
- **Соответствие**: Соблюдение требований по обработке текстовых данных

#### 4.6. Издержки  

- **Расчетные издержки**: GPU время ~$50-100/месяц для экспериментов
- **Оптимизация**: Использование LoRA снижает требования к ресурсам в 10x

#### 4.7. Integration points  

- **Взаимодействие**: REST API для интеграции с внешними системами
- **Форматы**: JSON для входных/выходных данных

#### 4.8. Риски  

- **Технические риски**: Переобучение, нехватка данных
- **Бизнес-риски**: Ограниченная применимость к другим языкам
- **Меры**: Регулярная валидация, расширение датасета

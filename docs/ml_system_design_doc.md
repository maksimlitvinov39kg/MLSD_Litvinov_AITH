### 1. Цели и предпосылки 
#### 1.1. Зачем идем в разработку продукта?  

- **Бизнес-цель**: Создание специализированного фреймворка для дообучения Vision-Language Model (VLM) с использованием LoRA (Low-Rank Adaptation) для описания русских персонажей на изображениях
- **Почему станет лучше**: Существующие VLM плохо понимают русские культурные персонажи и контексты. Специализированное дообучение позволит улучшить качество описания русских персонажей на изображениях
- **Критерии успеха итерации**: Создание рабочего MVP фреймворка с демонстрацией улучшения качества описания русских персонажей на тестовом датасете изображений

#### 1.2. Бизнес-требования и ограничения  

- **Бизнес-требования**: 
  - Создание воспроизводимого фреймворка для LoRA дообучения VLM
  - Поддержка различных архитектур Vision-Language моделей
  - Возможность быстрого прототипирования и экспериментов с изображениями
  - Документированный процесс дообучения для описания русских персонажей
- **Бизнес-ограничения**: 
  - Ограниченные вычислительные ресурсы (GPU)
  - Необходимость сохранения базовых способностей модели
  - Требования к воспроизводимости экспериментов
- **Ожидания от итерации**: Создание MVP фреймворка с примером дообучения на изображениях русских персонажей
- **Бизнес-процесс пилота**: Тестирование фреймворка на датасете изображений с русскими персонажами с измерением CLIP Score
- **Критерии успешного пилота**: Улучшение CLIP Score с ruCLIP для описания русских персонажей по сравнению с базовой VLM (конкретные метрики будут определены после тестирования)

#### 1.3. Что входит в скоуп проекта/итерации, что не входит   

- **Входит в скоуп**:
  - Создание базового фреймворка для LoRA дообучения VLM
  - Подготовка датасета изображений с русскими персонажами
  - Реализация пайплайна дообучения для описания изображений
  - Базовые метрики оценки качества (CLIP Score с ruCLIP, human-eval)
  - Streamlit WebUI для демонстрации и тестирования модели
  - Документация по использованию и развертыванию
- **Не входит в скоуп**:
  - Production-ready REST API с масштабированием
  - Автоматическое масштабирование и load balancing
  - Продвинутые техники оптимизации (quantization, distillation)
  - Полнотекстовая система аутентификации и авторизации
  - Интеграция с внешними системами мониторинга
- **Результат с точки зрения качества кода**: 
  - Чистый, документированный код с примерами использования
  - Воспроизводимые эксперименты с фиксированными seeds
  - Модульная архитектура (разделение train/eval/inference)
  - Готовый к демонстрации интерактивный сервис
- **Технический долг**: 
  - Отсутствие полного логирования и мониторинга
  - Ограниченная поддержка различных форматов данных
  - Отсутствие REST API (только WebUI)
  - Синхронный инференс (без параллелизма)

#### 1.4. Предпосылки решения  

- **Блоки данных**: Датасет изображений с русскими персонажами и их текстовые описания
- **Горизонт прогноза**: Не применимо (задача генерации текста по изображению)
- **Гранулярность модели**: Описание изображений на уровне персонажей и их характеристик
- **Частота пересчета**: По требованию (offline обучение)
- **Обоснование**: LoRA позволяет эффективно дообучать большие VLM с минимальными вычислительными затратами, сохраняя базовые способности модели

### 2. Методология     

#### 2.1. Постановка задачи  

- **Техническая задача**: Создание системы дообучения Vision-Language Model (VLM) с использованием LoRA для описания русских персонажей с изображений
- **Тип задачи**: Supervised Fine-Tuning (SFT) для задачи генерации текстовых описаний изображений с русскими культурными персонажами
- **Цель**: Адаптировать предобученную VLM для лучшего понимания и описания русских культурных персонажей на изображениях

#### 2.2. Блок-схема решения  

```
[Изображения с русскими] → [Подготовка датасета] → [Предобработка] → [LoRA дообучение] → [Валидация] → [Тестирование] → [Деплой модели]
[персонажами]            ↓                    ↓                ↓                ↓              ↓              ↓
                        [Разметка описаний]  [Vision Encoder] [Fine-tuning]   [CLIP Score]  [Image-to-Text] [Модель готова]
                        [Train/Val/Test]    [Text Decoder]   [LoRA layers]   [ruCLIP]     [Generation]    [к использованию]
```

#### 2.3. Этапы решения задачи  

**Этап 1 - Подготовка данных**

- **Данные и сущности**: Датасет изображений с русскими персонажами и их текстовые описания для обучения VLM

| Название данных  | Есть ли данные в компании | Требуемый ресурс для получения данных | Проверено ли качество данных |
| ------------- | ------------- | ------------- | ------------- |
| Изображения русских персонажей | Собственная коллекция | DS/Designer | - |
| Текстовые описания персонажей | Собственная разметка | DS/Annotator | - |
| Культурные контексты | Собственная разметка | DS/Annotator | - |
| Валидационные изображения | Публичные датасеты | DS | - |

- **Результат этапа**: Подготовленные и размеченные данные в формате для обучения, разделенные на train/validation/test

**Этап 2 - Настройка LoRA дообучения**

- **Формирование выборки**: 80% train, 10% validation, 10% test с сохранением разнообразия русских персонажей
- **Горизонт и гранулярность**: Генерация текстовых описаний изображений, пересчет по требованию
- **Целевая переменная**: Текстовые описания русских персонажей на изображениях
- **Метрики качества**: 
  - CLIP Score с использованием ruCLIP для оценки соответствия между сгенерированным текстом и изображением
  - Улучшение CLIP Score относительно базовой модели (масштаб улучшения будет определен экспериментально)
- **Необходимый результат**: Рабочая VLM с улучшенным описанием русских персонажей на изображениях
- **Риски**: Недостаток размеченных данных изображений, переобучение на специфических персонажах
- **Принципы**: Использование LoRA для эффективного дообучения, сохранение базовых способностей VLM
- **Бизнес-проверка**: Тестирование на реальных изображениях с русскими персонажами

**Этап 3 - Валидация и тестирование**

- **Техника**: Кросс-валидация на размеченном датасете изображений, A/B тестирование с базовой VLM
- **Метрики**: Сравнение CLIP Score до и после дообучения с ruCLIP
- **Результат**: Валидированная VLM с подтвержденным улучшением качества описания русских персонажей

### 3. Подготовка пилота  

#### 3.1. Механизм проведения пилота  
Пилот проводится в offline-режиме с использованием **фиксированного тестового набора изображений**, включающего:
- **Целевые персонажи**: Чебурашка, Колобок, Алёша Попович, Крокодил Гена (~25 изображений на персонаж);
- **Контрольные персонажи**: Матрёшка, Человек-паук, Супермен (для оценки деградации базовых знаний).

Для каждого изображения выполняется:
1. Формирование запроса с использованием фиксированных промптов из `data/json/base_prompts.json`;
2. Генерация текстового описания двумя моделями:
   - **Baseline**: предобученная модель `Qwen/Qwen2.5-VL-3B-Instruct` без дообучения;
   - **Fine-tuned**: модель с загруженным LoRA-адаптером из `./results/.../final_model` (лучшая конфигурация — `lora_v2`);
3. Оценка качества ответов по двум методам:
   - **Human-eval**: ручная проверка корректности ответов по 3–4 вопросам на изображение (было реализовано в ноутбуках `test_after_finetune_*.ipynb`);
   - **ruCLIP Score**: автоматическая метрика семантического соответствия (дополнительно для будущих итераций).

Процесс полностью воспроизводим: зафиксированы seed, промпты, версии моделей и состав тестового набора (`assets/` + часть `val`).

#### 3.2. Способ оценки успешности  
Пилот считается **успешным**, если выполняются следующие условия:

- ✅ **Основной критерий (human-eval)**:
  - ≥2 из 4 целевых персонажей демонстрируют **устойчивое улучшение** (правильные ответы ≥75% вопросов);
  - Отсутствует **существенная деградация** на контрольных персонажах (ошибки ≤1 из 4 вопросов).

- ✅ **Дополнительные признаки качества**:
  - Снижение галлюцинаций по сравнению с baseline (особенно на персонажах, не входящих в датасет);
  - Устойчивость к переобучению (модель не путает персонажей, даже при схожей визуальной структуре, например, Чебурашка ↔ Колобок).

На основе проведённых экспериментов **лучший результат** показала конфигурация `lora_v2` (`lora_r=16`, `alpha=32`, `dropout=0.1`, `max_length=256`, 25 эпох):
- ✔️ Чебурашка и Крокодил Гена: 100% корректных ответов;
- ✔️ Колобок и Алёша Попович: частичное улучшение (требуется доработка датасета);
- ✔️ Контрольные персонажи: деградация отсутствует (кроме одного случая с Суперменом → «колибри» в `lora_v2`, что считается допустимым шумом).

#### 3.3. Подготовительные шаги  
Перед запуском пилота были выполнены следующие действия:
1. **Формирование и верификация датасета**:
   - Сгенерированы captions для ~25 изображений на целевого персонажа с помощью `caption_data.py`;
   - Выполнена ручная проверка качества аннотаций (удалены пустые/некорректные ответы);
2. **Фиксация baseline-поведения**:
   - Проведён `test_pretrain.ipynb` для оценки исходной модели на всех персонажах;
3. **Разделение данных**:
   - Создан `val`-сплит (15% от `annotation.json`) с сохранением баланса по классам;
   - Контрольные персонажи (`assets/`) добавлены вручную вне тренировочного датасета;
4. **Воспроизводимость**:
   - Зафиксированы seed, версия промптов, аппаратная конфигурация (MPS/CPU);
   - Все эксперименты залогированы в Weights & Biases;
5. **Оценочный pipeline**:
   - Реализованы ноутбуки `test_after_finetune_*.ipynb` с единым шаблоном запросов и оценки;
   - Результаты визуализированы в `result_charts/`.

### 4. Внедрение    

#### 4.1. Архитектура решения   

- **Компоненты**:
  - Data preprocessing pipeline (`train_qwen_with_lora.py`)
  - LoRA training framework с поддержкой Qwen2.5-VL-3B
  - Model evaluation tools (ноутбуки в `finetune_testing/`)
  - Inference API (Streamlit-приложение в `service/`)
  - WebUI сервис для интерактивного тестирования
- **API методы**: 
  - `train()` - обучение модели с LoRA адаптерами
  - `evaluate()` - оценка качества на тестовом наборе
  - `predict()` / `run_chat_with_lora()` - инференс с дообученной моделью
  - `load_model_with_lora()` - загрузка базовой модели и применение LoRA
- **Основные технологии**:
  - `transformers` - загрузка и работа с Qwen2.5-VL-3B
  - `peft` - реализация LoRA адаптеров
  - `streamlit` - WebUI для демонстрации возможностей
  - `torch` - вычисления на GPU/MPS/CPU

#### 4.2. Описание инфраструктуры и масштабируемости 

**Основная инфраструктура:**

1. **Training pipeline** (`train_qwen_with_lora.py`):
   - Локальное обучение на GPU/MPS/CPU
   - Сохранение чекпойнтов и LoRA адаптеров в `results/`
   - Интеграция с Weights & Biases для логирования

2. **Inference Service** (`service/app.py`):
   - Streamlit-приложение для интерактивного тестирования
   - Загрузка базовой модели Qwen2.5-VL-3B-Instruct
   - Динамическая загрузка LoRA адаптеров из указанного пути
   - Поддержка GPU/MPS/CPU (автоматический выбор устройства)
   - WebUI с загрузкой изображений и предустановленными промптами

3. **Evaluation pipeline** (`finetune_testing/test_after_finetune_*.ipynb`):
   - Воспроизводимое тестирование на фиксированном наборе изображений
   - CLIP Score оценка с ruCLIP
   - Human-eval оценка
   - Визуализация результатов

**Требования к ресурсам:**

- **Память**: ~8-12 GB RAM + GPU VRAM (3B модель требует ~6-8 GB)
- **Диск**: ~10 GB для моделей и результатов
- **Вычисления**: GPU (рекомендуется) или MPS (Apple Silicon) или CPU (медленно)

**Плюсы текущей архитектуры**: 
- Гибкость, контроль над данными
- Простота развертывания локально
- Модульная структура (разделение train/eval/inference)
- Поддержка различных устройств

**Минусы текущей архитектуры**: 
- Ограниченные ресурсы на локальной машине
- Необходимость ручного управления зависимостями
- Нет горизонтального масштабирования
- Streamlit сервис работает синхронно, без кэширования результатов

**Обоснование**: MVP требует простоты, контроля над процессом и возможности быстрого прототипирования. Модульная архитектура позволит в будущем перенести сервис на облако (AWS Lambda, Google Cloud Functions) или контейнеризировать (Docker).

#### 4.3. Требования к работе системы  

**Inference Service (Streamlit):**
- **SLA**: Real-time обработка пользовательских запросов
- **Время отклика**: Генерация описания изображения < 5 сек (в зависимости от GPU)
- **Пропускная способность**: Последовательная обработка запросов пользователя
- **Задержка**: ~1-2 сек для загрузки модели + ~1-3 сек для инференса
- **Максимальная длина ответа**: Настраивается в UI (64-512 токенов, по умолчанию 256)

**Training Pipeline:**
- **SLA**: Offline обучение, время выполнения 1 эпохи зависит от размера датасета
- **Пропускная способность**: Обработка батчей до 128 изображений
- **Воспроизводимость**: Фиксированные seed для гарантированной воспроизводимости

#### 4.4. Безопасность системы  

- **Уязвимости**: Потенциальные атаки на модель через adversarial examples
- **Меры**: Валидация входных данных, ограничение размера запросов

#### 4.5. Безопасность данных   

- **GDPR**: Использование только публичных датасетов, отсутствие персональных данных
- **Соответствие**: Соблюдение требований по обработке текстовых данных

#### 4.6. Издержки  

- **Расчетные издержки**: GPU время ~$50-100/месяц для экспериментов
- **Оптимизация**: Использование LoRA снижает требования к ресурсам в 10x

### 5. Сервис инференса (WebUI на Streamlit)

#### 5.1. Описание сервиса

**Файлы:**
- `service/app.py` - основное Streamlit приложение
- `service/requirements.txt` - зависимости сервиса
- `service/README.md` - инструкции по запуску

#### 5.2. Функциональность

**Основные возможности:**
1. **Загрузка изображений**: Поддержка форматов JPG, JPEG, PNG, WEBP
2. **Интерактивные промпты**: 
   - 5 предустановленных промптов для быстрого тестирования:
     - "Опиши подробно, что изображено на картинке."
     - "Кто или что находится на этом изображении?"
     - "Какие детали ты видишь на этой картинке?"
     - "Расскажи о персонаже на изображении."
     - "Что происходит на этой картинке?"
   - Возможность ввода собственного вопроса
3. **Инференс с LoRA**: Использование дообученной модели Qwen2.5-VL-3B-Instruct
4. **Конфигурируемые параметры**:
   - Путь к LoRA весам (по умолчанию: `../results/qwen-vl-regional/exp_r=16_alpha=32_seq=256_ne=25/checkpoint-430`)
   - Максимальная длина ответа: 64-512 токенов (по умолчанию 256)
5. **Визуализация**: Отображение загруженного изображения и сгенерированного описания

#### 5.3. Технические детали

**Загрузка модели:**
- Функция `load_model_with_lora()` с кэшированием через `@st.cache_resource`
- Автоматический выбор устройства: GPU (CUDA) → MPS (Apple Silicon) → CPU
- Обработка ошибок при загрузке LoRA адаптеров (fallback на базовую модель)
- Использование `AutoProcessor` для подготовки входов

**Инференс:**
- Функция `run_chat_with_lora()` для генерации описаний
- Применение chat template процессора
- Использование `qwen_vl_utils.process_vision_info()` для обработки изображений
- Параметры генерации: `max_new_tokens`, `do_sample=False` (детерминированный режим)
- Очистка промптов от служебных токенов в выходе

#### 5.5. Архитектурные решения

**Почему Streamlit:**
- ✅ Быстрое прототипирование WebUI без фронтенд-кода
- ✅ Встроенный кэширование для оптимизации памяти
- ✅ Интерактивность с минимальным кодом
- ✅ Автоматическое перезагружение при изменении файлов (во время разработки)

**Ограничения Streamlit (и пути решения):**
- ❌ Синхронная обработка (1 пользователь одновременно)
  - *Решение для production*: Миграция на FastAPI + uvicorn
- ❌ Нет встроенного аутентификации
  - *Решение*: Развертывание в приватной сети или за proxy с аутентификацией
- ❌ Полная переотправка HTML при каждом обновлении
  - *Решение*: Приемлемо для MVP, оптимизировать при необходимости

#### 4.7. Integration points  

**Текущая архитектура:**
- **Streamlit WebUI**: Интерактивный интерфейс для тестирования модели
  - Загрузка изображений через браузер
  - Предустановленные и пользовательские промпты
  - Real-time вывод результатов
  
**Будущие точки интеграции:**
- **REST API**: JSON-endpoint для интеграции с внешними системами
  - `POST /predict` - генерация описания изображения
  - `POST /batch-predict` - обработка нескольких изображений
  - `GET /model-info` - информация о текущей модели
- **Форматы обмена**: JSON для входных/выходных данных
- **Прямая интеграция**: Импорт модуля в Python-код через `from peft import PeftModel`

#### 4.8. Риски  

**Технические риски:**
- **Переобучение**: Модель может переобучиться на специфических русских персонажах
  - *Мера*: Валидация на контрольном наборе (Матрёшка, Супермен и т.д.), раннее останавливание
- **Нестабильность инференса на Streamlit**: Долгие времена загрузки модели
  - *Мера*: Кэширование модели с @st.cache_resource, оптимизация памяти
- **Деградация на других языках**: Возможна при узкой специализации
  - *Мера*: Включить в тестовый набор примеры на других языках
- **Нехватка памяти при инференсе**: Потребление VRAM может быть непредсказуемо
  - *Мера*: Использование quantization, gradient checkpointing, attention slicing

**Бизнес-риски:**
- **Ограниченная применимость**: Модель может работать плохо на не-русских персонажах
  - *Мера*: Четкое документирование ограничений, управление ожиданиями
- **Зависимость от Qwen**: Обновления базовой модели могут нарушить LoRA адаптеры
  - *Мера*: Зафиксировать версии dependencies в requirements.txt
- **Масштабируемость**: Текущая архитектура не поддерживает параллельный инференс
  - *Мера*: Миграция на FastAPI + uvicorn для production

**Операционные риски:**
- **Воспроизводимость**: Различные версии библиотек могут давать разные результаты
  - *Мера*: Фиксировать версии всех зависимостей, использовать контейнеры (Docker)
